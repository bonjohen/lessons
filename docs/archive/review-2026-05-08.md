# Project Review

**Date:** 2026-05-08
**Scope:** Full
**Project:** Lessons Hub (lessons-hub)
**Reviewer:** Claude Code

## Executive Summary

Lessons Hub is architecturally sound with clean separation between harvesting, validation, and rendering. The most significant finding is **unsanitized markdown rendering via `set:html`** — content from external GitHub repos is converted to HTML with `marked` and injected without sanitization, creating an XSS vector if any source repo is compromised. Secondary priorities: uncommitted production files from a recent refactor, duplicated validation logic between harvester and validator, zero integration/E2E tests, and duplicated CSS across 5 components.

## Findings

### [CRITICAL] F-01: Unsanitized markdown rendered via set:html

**Category:** Security
**Evidence:**
- `src/pages/lessons/[id].astro:17` — `const htmlContent = await marked(lesson.content);`
- `src/pages/lessons/[id].astro:46` — `<Fragment set:html={htmlContent} />`
- `lesson.content` originates from external GitHub repos cloned at build time
- `marked` v18.x does not sanitize HTML by default — `<img src=x onerror=alert(1)>` in markdown passes through to rendered output

**Impact:** If any source repository is compromised or a contributor adds malicious HTML to a lesson markdown file, arbitrary JavaScript executes in every visitor's browser. The static build doesn't filter it.
**Fix:** Install `sanitize-html` (lighter than DOMPurify for server-side/build-time use) and sanitize before rendering:
```typescript
import sanitizeHtml from 'sanitize-html';
const htmlContent = sanitizeHtml(await marked(lesson.content));
```

### [HIGH] F-02: Uncommitted production files break CI

**Category:** Operations
**Evidence:**
- `git ls-files --others --exclude-standard` shows untracked: `scripts/lesson_core.py`, `tests/conftest.py`, `pyproject.toml`
- `scripts/harvest_lessons.py:15-26` imports from `lesson_core`
- `scripts/validate_lessons.py:10-15` imports from `lesson_core`
- All 4 test files import from `lesson_core` via `conftest.py` sys.path setup
- CI workflow (`build-deploy.yml:43-49`) runs `npm run harvest` and `npm run validate:lessons`, which will fail with `ModuleNotFoundError`

**Impact:** The next push to `main` will break the CI/CD pipeline. The site cannot be built or deployed until these files are committed.
**Fix:** `git add scripts/lesson_core.py tests/conftest.py pyproject.toml` and commit.

### [HIGH] F-03: Duplicated validation logic between harvester and validator

**Category:** Architecture
**Evidence:**
- `scripts/harvest_lessons.py:183-192` — inline validation checks against `VALID_LESSON_TYPES` and `VALID_STATUSES`
- `scripts/lesson_core.py:127-176` — canonical `validate_lesson_record()` with the same checks
- `scripts/validate_lessons.py:96-108` — calls `validate_lesson_record()` correctly

The harvester validates during parsing (lines 183-192) using imported constants but its own `warn()` calls, while the validator delegates to `validate_lesson_record()`. If controlled vocabularies change, the harvester's inline checks and `validate_lesson_record()` could produce different warnings for the same lesson.

**Impact:** Divergent validation between harvest-time and validate-time. A lesson could pass harvesting but fail validation (or vice versa) for the same field.
**Fix:** Remove inline validation from `parse_lesson()` in `harvest_lessons.py` (lines 172-192). The validator already runs `validate_lesson_record()` on all harvested records. Harvester should focus on parsing; validator should own all validation.

### [HIGH] F-04: Zero integration or end-to-end tests

**Category:** Tests
**Evidence:**
- 43 unit tests in `tests/` — all test `lesson_core.py` pure functions
- No test creates a temporary repo structure, runs `harvest_lessons.main()`, and verifies output JSON
- No test runs `validate_lessons.main()` against generated data
- `parse_lesson()`, `scan_lessons()`, `generate_indexes()`, `generate_exports()`, `load_repos()` — all untested
- Full pipeline (`npm run build:full`) has never been tested in isolation

**Impact:** Regressions in the harvesting pipeline, JSON generation, or cross-module integration are invisible until a real build fails. The unit tests cover leaf functions but not the glue.
**Fix:** Add `tests/test_harvest_integration.py` with a fixture that creates a minimal repo structure (repos.yml + lesson markdown files in a temp dir), patches `TMP_DIR` and `REPOS_YML`, runs `main()`, and asserts the generated JSON files exist and contain expected records.

### [MEDIUM] F-05: CLAUDE.md references nonexistent script

**Category:** Documentation
**Evidence:**
- `CLAUDE.md:37` — `python scripts/build_exports.py      # Generate AI export packs`
- File does not exist: `scripts/build_exports.py` is not on disk or in git
- Export functionality is integrated into `scripts/harvest_lessons.py:324-377` (`generate_exports()`)
- Design rationale documented in `docs/lessons/harvester-design-decisions.md`

**Impact:** Developers or AI assistants following CLAUDE.md instructions will get a `FileNotFoundError`. Misleading documentation for the primary project reference file.
**Fix:** Remove line 37 from CLAUDE.md or replace with a comment noting exports are generated by the harvester.

### [MEDIUM] F-06: Inconsistent error handling between scripts

**Category:** Consistency
**Evidence:**
- `scripts/harvest_lessons.py:38-45` — `warn()` / `error()`, appends to lists, prints to `sys.stderr`
- `scripts/validate_lessons.py:27-42` — `log_error()` / `log_warning()` / `log_info()`, uses global counters, prints to `stdout`
- Different naming: `warn` vs `log_warning`, `error` vs `log_error`
- Different output streams: stderr vs stdout
- Different tracking: list append vs global int counter

**Impact:** Inconsistent behavior when piping output or parsing logs. Errors from harvesting go to stderr; errors from validation go to stdout. Makes CI log parsing unreliable.
**Fix:** Standardize both scripts to use the same output stream (stderr for errors/warnings) and the same naming convention. Consider extracting a shared logging helper into `lesson_core.py`.

### [MEDIUM] F-07: Duplicated tag CSS across 5 components

**Category:** Consistency
**Evidence:**
- `src/components/LessonCard.astro:74-84` — `background: #e8f0fe; color: #1a56db; padding: 0.15em 0.5em;`
- `src/components/RepoCard.astro:51-58` — same colors, same padding
- `src/components/TagList.astro:18-25` — same colors, **different padding**: `0.2em 0.6em`
- `src/pages/tags/index.astro:31-47` — same colors, **different padding**: `0.3em 0.7em`
- `src/pages/tags/[tag].astro:62-66` — same colors, padding `0.2em 0.6em`

Three different padding values for the same visual element.

**Impact:** Inconsistent tag appearance across pages. Changing the tag design requires editing 5 files and knowing about the padding variants.
**Fix:** Create a shared `.tag` class in `BaseLayout.astro` global styles or a dedicated `src/styles/tags.css` imported by all components.

### [MEDIUM] F-08: Duplicated breadcrumb styles across 5 pages

**Category:** Consistency
**Evidence:**
- `src/pages/lessons/[id].astro:86-90` — `.breadcrumb { font-size: 0.85rem; color: #777; margin-bottom: 1rem; }`
- `src/pages/repos/[repo].astro:54-59` — identical
- `src/pages/tags/[tag].astro:59` — identical
- `src/pages/phases/[phase].astro:27-28` — identical
- `src/pages/types/[type].astro:26-27` — identical

**Impact:** Same as F-07 — changing breadcrumb styling requires editing 5 files.
**Fix:** Move `.breadcrumb` to `BaseLayout.astro` global styles (it's already the common layout wrapper).

### [MEDIUM] F-09: @ts-nocheck disables all TypeScript checking in data.ts

**Category:** Architecture
**Evidence:**
- `src/lib/data.ts:1` — `// @ts-nocheck — JSON imports are untyped; we cast them below`
- Lines 65-83 use `as unknown as Lesson[]` and similar unsafe casts for all 5 data loaders
- The `Lesson` interface (lines 8-33) defines 24 fields but no runtime validation confirms the JSON matches

**Impact:** Type errors in generated JSON are invisible. If the Python harvester changes a field name or type, TypeScript won't catch it — the `@ts-nocheck` suppresses all errors in the file, not just the import-related ones.
**Fix:** Remove `@ts-nocheck`. Use narrower `@ts-expect-error` comments on the specific import lines, or define a Zod schema matching the interface for runtime validation.

### [LOW] F-10: Magic numbers for display limits

**Category:** Architecture
**Evidence:**
- `src/pages/index.astro:14` — `.slice(0, 10)` (recent lessons)
- `src/pages/lessons/[id].astro:23` — `.slice(0, 5)` (related lessons)
- `src/components/RepoCard.astro:20` — `.slice(0, 8)` (tags per repo card)
- `src/pages/tags/[tag].astro:45` — `.slice(0, 15)` (related tags)
- `scripts/lesson_core.py:200` — `word_count / 200` (reading speed WPM)
- `scripts/lesson_core.py:173` and `scripts/harvest_lessons.py:191` — `50` (min content words, duplicated)

**Impact:** Minor. Changing a limit requires finding it in the code. The duplicated `50` in two files could drift.
**Fix:** Extract Python constants to `lesson_core.py` (`MIN_CONTENT_WORDS = 50`, `READING_WPM = 200`). For Astro, a shared `src/lib/constants.ts` for display limits is optional polish.

### [LOW] F-11: No Content Security Policy headers

**Category:** Security
**Evidence:**
- No CSP meta tag in `src/layouts/BaseLayout.astro`
- No `public/_headers` file for GitHub Pages
- No CSP configuration in `astro.config.mjs`

**Impact:** Low for a static site with no inline scripts (aside from Pagefind), but CSP would provide defense-in-depth against F-01 (XSS).
**Fix:** Add `public/_headers` with a restrictive CSP policy once F-01 is resolved.
